## Allowlist key names

Each channel has its own `[channels.<slug>]` block with channel-specific keys. The allowlist key name varies:

| Channel | Allowlist key | Default behavior on empty |
|---|---|---|
| `telegram` | `allowed_users` | Offline (deny-all) |
| `discord` | `allowed_users` | Offline |
| `slack` | `allowed_users` | Offline |
| `mattermost` | `allowed_users` | Offline |
| `matrix` | `allowed_users` | Offline |
| `irc` | `allowed_users` | Offline |
| `dingtalk` | `allowed_users` | Offline |
| `lark` | `allowed_users` | Offline |
| `qq` | `allowed_users` | Offline |
| `nextcloud_talk` | `allowed_users` | Offline |
| `imessage` | `allowed_contacts` | Offline |
| `signal` | `allowed_from` | Offline |
| `whatsapp`, `whatsapp_web` | `allowed_numbers` | Offline |
| `email_channel` | `allowed_senders` | **Allow-all** (exception) |
| `linq` | `allowed_senders` | (per-deployment) |

Most allowlists support a wildcard entry `"*"` to allow-all explicitly. Email's `allowed_senders` accepts both full addresses (`alice@example.com`) and domain prefixes (`@example.com`).

## Common config keys (per channel)

| Key | Description |
|---|---|
| `bot_token` / `app_token` | Channel-specific auth credential (encrypted as `enc2:<hex>`) |
| `allowed_*` | Allowlist (see above) |
| `enabled` | Toggle the channel without deleting its config |

For complete per-channel schemas (transport-specific keys, app secrets, signing tokens), see the upstream `docs/channels-reference.md` until this site has its generated reference.

## Notable channel-specific behavior

- **Telegram** supports runtime allowlist mutation — `add_allowed_identity_runtime` lets the agent add an allowed user without restart. No other channel currently supports this.
- **Email** is the only channel that allows-all on empty allowlist. Set explicit `allowed_senders` to restrict.
- **Discord** and **Slack** support the channel-trait draft-update API — the agent can edit a sent message in place. Useful for streaming responses incrementally.
- **WhatsApp Cloud (`whatsapp`)** uses Meta's `X-Hub-Signature-256` HMAC verification on incoming webhooks (when `app_secret` is set).
- **Matrix** requires the `channel-matrix` feature at build time and uses `matrix-sdk` for E2EE.
- **WhatsApp Web (`whatsapp_web`)** requires the `whatsapp-web` feature; uses `wa-rs` with a custom rusqlite storage backend.

## Channel restart behavior

Channels are supervised by the daemon with backoff:

```toml
[reliability]
channel_initial_backoff_secs = 2
channel_max_backoff_secs = 60
```

A channel that fails to connect retries with exponential backoff up to the cap. Other channels are unaffected.

## Approval reply protocol (v0.6.5+)

When the agent's `shell` tool hits a basename that isn't on the static allowlist in `Supervised` autonomy mode, the tool suspends and the agent's reply explains the failure to the user. The user can resolve the suspension by replying on the same channel with one of these tokens:

| Token | Action | Persistence |
|---|---|---|
| `/allow brew` or `allow brew` | Add `brew` to runtime allowlist | session only |
| `/allow brew --persist` or `allow brew persist` or `allow brew -p` | Add and write to disk | survives restart |
| `/deny brew` or `deny brew` | Reject; agent's tool call fails | n/a |
| `y brew` | Short form: allow once | session only |
| `Y brew` (capital) | Short form: allow + persist | survives restart |
| `n brew` | Short form: deny | n/a |

The dispatch loop's parser (`src/channels/approval_relay.rs::try_handle_reply`) is **strict by design**:

- Extra words past `--persist` are rejected (so "allow brew because I need it" doesn't silently approve).
- The first token must be a known verb (so `find / -name foo` won't parse as a slash command).
- The basename token must be a single word — multi-word args are rejected.

On a successful parse, the channel sends an ack message ("✅ Added `brew` to the session allowlist — pending approval resolved; the agent will retry") and the suspended turn resumes. On a chatty/unrecognized message, the parser returns `None` and the message routes to the agent as a normal turn input.

The reply parser runs **before** the inbound message dispatcher in `run_message_dispatch_loop`, so resolving an approval doesn't burn an agent turn.

## Hot-reload caveat

Editing `config.toml` to add a `[channels_config.<name>]` block fires the **config watcher** (since v0.6.37) and rebuilds the agent. **The new channel's listener task is not auto-spawned** — the agent reload only refreshes config, not running supervisor tasks. A system message tells you to restart for the listener to come online:

```text
⚠ 1 new channel(s) configured. Restart rantaiclaw to start polling them. /channels shows the current state.
```

Auto-spawn of channel listeners after hot-reload is a v0.6.8 deliverable.
